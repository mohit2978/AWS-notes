# Part 1: Networking & Web Architecture Fundamentals

## 1. Architecture

**Client** is one who requests a resource. **Server** is the one which responds to the request of that resource.

![Client Server Architecture](images/001_1a_client_server_architecture.svg)

Both should be in the same network. Each device (hub/switch) can be either client or server — if it is requesting then it is a client, if fulfilling the request then it is a server.

---

### Types of Architecture

#### 1-Tier Architecture
You develop your code on local — no one else can access it. DB is also on the same computer. Your laptop acts as both client and server. It is **not good** to keep client and server on the same machine.

#### 2-Tier Architecture

Logic and DB in the server; UI in a different machine.

![2-Tier Architecture](images/001_1b_2tier_architecture.svg)

If there are memory issues (Application and DB taking too much space), the server might crash — like Tatkal ticket booking on IRCTC. So it is **not good** to keep Application and DB on the same machine.

**Advantages of Two-Tier Client/Server Structure:**
- Easy to maintain and modify.
- Communication between client and server (request/response) is quite fast.

**Disadvantages of Two-Tier Client/Server Structure:**
- If client nodes increase beyond capacity, the server cannot handle the request overflow and performance degrades.

To test code before going to production, code is tested in a **Test Environment**. After testing we have a **Pre-Prod environment** (similar to prod).

![Dev to Test to Pre-Prod to PROD Environment Flow](images/001_2_dev_prod_preprod_test_flow.svg)

#### 3-Tier Architecture

The disadvantage of 2-tier is that application and DB are in the same environment causing memory issues. So we separate them — that gives us 3-tier.

![3-Tier Architecture](images/001_3_3tier_architecture.svg)

- **IP** is the unique identifier of a computer in a network (like an Aadhar card for a person).
- Your **application server** must be in a private network — we do not want everyone to see the code.
- The **client** is in a public network. To let the client access the app server, we use a **Web Server** — it takes requests from the client and redirects to the application server. No code lives here.

#### N-Tier (Microservices)
Each service runs independently and communicates over the network.

## 2. DNS (Domain Name System)

![DNS Resolution Flow](images/001_4_dns_resolution_and_servers.svg)

You access `google.com`. The hostname is `google.com`, but the browser understands IP addresses. Remembering every website's IP address is impractical — that is why DNS exists.

**DNS is like a distributed map of `<Hostname, IP Address>`.**
The local cache is called **Local DNS**.

### Steps to Resolving a Domain Name

1. Web browser and OS first check whether the domain is in their **cache**. If yes, done.
2. The browser sends a request to a **DNS Resolver** (a local server hosted with your ISP).
3. The resolver checks its cache. If not found, it queries **Root Name Servers** recursively.
4. Root servers respond with the address of the **Top-Level Domain (TLD)** server (e.g., `.com`).
5. The TLD server responds with the **Authoritative Name Server** for `google.com`.
6. The Authoritative Name Server responds with the **IP address** of `www.google.com`.
7. The resolver caches this IP, and the OS also caches it for future use.

> DNS is organized in an upside-down tree-like structure — we go to the top (Root) and search downward.

![Root Name Server — Laptop via Local DNS](images/001_6a_root_name_server_laptop.svg)

The Root Name Server checks the domain extension (`.com`, `.uk`, etc.) and routes accordingly.

![Top Level Domain Identified by Root Name Server](images/001_6b_top_level_domain_arrows.svg)

The Root Name Server sends the request to the `.com` Top-Level Domain.

![Srinivas Request Path through Local DNS, RNS, TLD to .com Domains](images/001_7_srinivas_request_and_com_domains.svg)

Among all `.com` domains, we now find `google.com` using the **Name Server** (NS) which identifies the hostname, and then routes to the **SOA (Start of Authority)** record where we get the IP.

**What is a DNS SOA record?**
The DNS *Start of Authority* (SOA) record stores important info about a domain/zone: the administrator's email, when the domain was last updated, and how long the server should wait between refreshes. All DNS zones need an SOA record to conform to IETF standards.

![Full DNS Lookup Flow: NS/SOA to TLD to RNS to Local DNS to Browser](images/001_8_full_dns_lookup_flow.svg)

## 3. Firewall

Now that we have the IP address, we can reach the Google server. At that server there is a **Firewall** — which allows/blocks traffic by allow and deny rules.

![DNS Lookup Flow with Firewall at Google Company](images/001_9a_dns_lookup_plus_firewall.svg)

On the firewall we put rules like: **disallow HTTP, allow HTTPS**.

![Default Protocol Port Numbers Table](images/001_9b_protocol_port_table.svg)

| Protocol | Port |
|----------|------|
| HTTP     | 80   |
| HTTPS    | 443  |
| SSH      | 22   |
| RDP      | 3389 |

- **HTTP** — not a secure connection to a website.
- **HTTPS** — secure connection to a website.
- **SSH** — used to connect to Linux machines.
- **RDP** — used to connect to Windows machines.

> **Firewall stops unauthorized access to the network.**

## 4. Load Balancer

On a Google request, it first goes to the **Web Server**, then **App Server**, then **DB Server**.

![Firewall with Grid of WebServer, App Server, DB Server inside Google Company](images/001_10a_firewall_grid_9_servers.svg)

The request goes to one of multiple web servers.

![Three Application Servers with Private IPs](images/001_10b_three_application_servers_ips.svg)

A user needs a domain name, not 3 raw IPs. That is why we use a **Load Balancer** which exposes a hostname.

![Load Balancer Distributing Traffic to 3 Application Servers](images/001_11_load_balancer_to_app_servers.svg)

> **Load Balancer distributes traffic to multiple servers using Round Robin.**

The name of the load balancer is the domain name. It is **exposed to the public**.

![Firewall plus Load Balancer plus Grid of WebServer, App Server, DB Server](images/001_12a_firewall_lb_grid_9_servers.svg)

If a website is not working, you check: Firewall → Load Balancer → Servers.

## 5. HTTP

### DNS Done — Now HTTP

The browser follows **HTTP (HyperText Transport Protocol)** to send a GET request to google.com.

![HTTP GET Request/Response Flow between Client and Server](images/001_12b_http_get_request_flow.svg)

- HTTP is the protocol used to transfer data to and from a website.
- `WWW` indicates it is a website using the HTTP protocol.
- `HTTP://anything.com`, `WWW.anything.com`, `HTTP://WWW.anything.com` all lead to the same site.

**HTTP default port number is 80** (not 8080).

**URL Syntax:** `Protocol :// DomainName : Port`

We never include the port number in URLs because HTTP defaults to 80 and HTTPS defaults to 443 — the browser infers it from the protocol.

> If you use a non-default port (e.g., `https://google.com:143`), the browser returns an `ERR_UNSAFE_PORT` error — customers never need to remember port numbers.

```
HTTP  = HyperText Transfer Protocol    -> http://google.com
HTTP  default port = 80                -> Protocol :// DomainName : Port
HTTPS default port = 443               -> Always use 80 or 443 for customers
```

### Application Server Port Mapping

![Tomcat App Server on Port 8080](images/001_14_tomcat_8080_app_server.svg)

Tomcat runs on port 8080 internally. However, we **never expose raw IPs and port 8080** to customers.

![Load Balancer Forwarding to App Servers on 8080 Wrong Way](images/001_15a_lb_to_app_8080_ports.svg)

The **correct way**: The Load Balancer maps port **80 to 8080** internally. Customers only see the default port.

![Load Balancer Port Mapping 80 to 8080 to 80](images/001_15b_lb_port_mapping_80_to_8080.svg)

> Inside the server you can use any port, but the **Load Balancer always exposes the default port externally**.

### HTTP Data Format

HTTP transfers data as **hypertext** (formatted text). HTTP request/response messages include headers:

![HTTP Request Headers Example](images/001_16_http_request_headers_table.svg)

### HTTP Response Status Codes

Responses are grouped in five classes:

| Range     | Category                |
|-----------|-------------------------|
| 100–199   | Informational responses |
| 200–299   | Successful responses    |
| 300–399   | Redirection messages    |
| 400–499   | Client error responses  |
| 500–599   | Server error responses  |

**Common codes:**
- `200` — Page found / Success
- `404` — Page Not Found
- `500` — Internal Server Error (internal service is down)
- `503` — Service Unavailable (server down)

### HTTP Disadvantage — Not Secure

HTTP sends all data as **clear text** over the network.

![HTTP Data Packet Intercepted by a Hacker](images/001_17_http_data_packet_hacker.svg)

If you put a credit card number or CVV, HTTP sends it in plain text — anyone on the network can read it.

## 6. HTTPS (HTTP Secure)

We use **HTTPS** — all data is in encrypted format. Always check you are using HTTPS.

This security relies on **SSL/TLS Certificates** (also called HTTPS certificates), obtained from providers like GoDaddy.

> **Tomcat** is an application server; **Nginx** is a web server.

## 7. HTTP Over TCP/IP

**TCP** connects two servers via a **3-Way Handshake**. HTTP/HTTPS protocols work on top of TCP.

> TCP is like a bridge; HTTP/HTTPS packets are people crossing it.
> Or: TCP is the **track**, HTTP packets are the **metro trains**.

![HTTP over TCP/IP: Server 1 connected to Server 2 via TCP](images/001_19a_server1_tcp_server2.svg)

**UDP (User Datagram Protocol)** is an alternative — but it is **not reliable** (no guaranteed delivery).

## 8. OSI Model

![7 Layers of the OSI Model](images/001_19b_osi_7_layers_table.svg)

The 7 layers (bottom to top):

| # | Layer        | Role                                        |
|---|--------------|---------------------------------------------|
| 1 | Physical     | Physical hardware connection                |
| 2 | Data Link    | Node-to-node data transfer (MAC)            |
| 3 | Network      | Routing via IP addresses                    |
| 4 | Transport    | TCP/UDP — reliable delivery                 |
| 5 | Session      | Manages sessions between hosts              |
| 6 | Presentation | Encryption, compression, formatting         |
| 7 | Application  | HTTP, FTP, SMTP — end user facing           |

**Analogy (Boy meets Girl at a bus stop):**

1. Both need to be **physically present** — Physical Layer
2. They communicate via **speech** (data link in networks) — Data Link Layer
3. Both are at the **same bus stop** (same network) — Network Layer

![Boy (HOST 1) and Girl (HOST 2) in the Same Network Physical Layer](images/001_20a_boy_girl_physical_layer.svg)

4. A **friend** (TCP) establishes a connection between them. If it is a UDP friend — he is not trusted! — Transport Layer

![Boy (HOST 1) and Girl (HOST 2) Connected via TCP](images/001_20b_boy_girl_tcp_connection.svg)

5. The connection is established — now they have a **private session** — Session Layer
6. He **presents** himself to the girl — Presentation Layer
7. They go to a **movie together** — Application Layer

# Part 2: Cloud Computing Concepts



---

## 1. Server Room / Data Center

A data center contains wires, servers, and CPUs, typically handled by 1–10 people who manage all resources.

**Common data center problems:**
- A cleaning person trips on a wire → 8 hours of downtime and thousands of dollars lost
- Hard disk crashes → customers lose data; recovery depends on vendor
- Rats eat wires
- Servers need physical space (rooms) to be housed

When a business wants to host a website, an operations person buys a physical server. As traffic grows, more servers are added. This room of servers is the **data center**.

![Data Center Room: 4x4 Grid of Server Racks](images/1_2_datacenter_room_grid.svg)

**On-Premises**: A data center handled by your own team is called **on-premises**. This requires significant effort — adding/removing servers is entirely manual and physical.

Servers also have warranties. After the warranty expires, you must replace the hardware. New servers bring new issues.

---

## 2. Virtualization

After struggling with physical machines, a new technology appeared: **Virtualization**.

**Virtualization Concept:**
- Creating a virtual machine (VM) over an existing OS and hardware is called **Virtualization**.
- VMs provide an environment **logically separated** from the underlying hardware.
- The machine on which the VM is created = **Host Machine**; the VM itself = **Guest Machine**.
- The software/firmware that manages VMs = **Hypervisor**.

**Before Virtualization:**
- Single OS image per machine
- Software and hardware tightly coupled
- Running multiple apps on the same machine often creates conflicts
- Underutilized resources
- Inflexible and costly infrastructure

**After Virtualization:**
- Hardware-independence of OS and applications
- VMs can be provisioned to any system
- OS and application managed as a single unit by encapsulating them into VMs

**Virtualization Approaches:**
- **Hosted Architecture**: Installs and runs as an application. Relies on host OS for device support and physical resource management.
- **Bare Metal (Hypervisor) Architecture**: Hypervisor is installed directly on hardware — no host OS required. Results in better performance, scalability, and stability.

![Physical Machine vs Virtual Machine — Traditional vs Virtualized Stack](images/1_6a_traditional_vs_virtualized_stack.svg)

Setting up a physical machine takes at least 3 hours. A VM can be created and deleted in minutes — just need an OS. VMs use the host machine's hardware. The number of VMs you can create depends on the available hardware.

> Example: Need 100 machines? Use 5 big physical machines + 95 VMs.

10–11 years ago, most physical machines migrated to VMs.

---

## 3. Cloud Computing — The Move to AWS

With more VMs, risk increased. A new idea emerged: **a company (AWS) that manages the entire data center for you.**

AWS said to every customer: *"I will handle the data center — no need to set up your own."*

This migration from virtual machines to AWS is called **V2C Migration** (Virtual to Cloud).

**AWS Key Facts:**
- AWS has data centers throughout the globe
- In India: Mumbai and Hyderabad
- Mumbai is preferred (Hyderabad is newer, and newer infra may have bugs — like avoiding a newly opened restaurant)
- AWS uses **Xen Virtualization Technology** (like VMware, but AWS's own)

![Mumbai and Hyderabad as Remote Location Clouds Connected by Internet](images/1_9_mumbai_hyderabad_remote_location.svg)

**Cloud terminology:**
- Sitting here and accessing a remote location computer = **Cloud**
- Remote Location = Data Centers
- Data Center = Infrastructure (servers, storage, databases, etc.)

**Cloud Computing:**
> Instead of doing computing on a local machine / on-premises, you do computing in a Remote Location (Cloud). That is called **Cloud Computing**.

**Summary points:**
- We need the internet to connect to the Cloud
- AWS is a Cloud Provider who provides **Infrastructure as a Service**
- AWS is a group of services
- You access AWS through the **Amazon Management Console (AMC)**

## 4. Deployment Models (Types of Cloud)

**Analogy:** A restaurant only for family members = private. A restaurant open for everyone = public.

- **Public Cloud**: Accessible by everyone (e.g., AWS, Azure, GCP). Less secure due to openness.
- **Private Cloud**: Accessible only within an organization (e.g., Samsung Cloud Platform — SCP). More secure due to private nature.
- **Hybrid Cloud**: Public + Private. Example: A bank puts user profiles on AWS but handles transactions via a private cloud.
- **Community Cloud**: Systems accessible by a group of organizations.

![Public Cloud Model](images/1_11_public_cloud_model.svg)

**Public Cloud — Benefits:** Cost Effective, Reliability, Flexibility, Location Independence, Utility Style Costing, High Scalability  
**Public Cloud — Disadvantages:** Low Security, Less customizable

![Private Cloud Model](images/1_12a_private_cloud_model.svg)

**Private Cloud — Benefits:** Higher Security and Privacy, More Control, Cost and Energy Efficiency  
**Private Cloud — Disadvantages:** Restricted Area, Inflexible Pricing, Limited Scalability, Additional Skills Required

![Hybrid Cloud Model](images/1_12b_hybrid_cloud_model.svg)

**Hybrid Cloud — Benefits:** Best of both worlds — security of private + scalability of public  
**Hybrid Cloud — Disadvantages:** Complexity in management and integration

![Community Cloud Model](images/1_13_community_cloud_model.svg)

**Community Cloud — Benefits:** Cost effective, Sharing between organizations, Security  
**Community Cloud — Issues:** Data is shared at one location — must be careful; responsibility for governance, security, and cost allocation is challenging.

**Evolution path:**
```
Physical DC --> Virtualization --> Cloud --> AWS (Remote Location / Data Centers)
```

**Key terms:** Virtualization, Host Machine, DNS, VMs, Infrastructure, DataCenters, Load Balancer, Firewalls, Protocols, Hypervisor, Cloud, Remote Location

## 6. IaaS — Infrastructure as a Service

AWS is the most well-known IaaS provider. A person with a zip file of Java code gives it to AWS. AWS says: *"I provide everything — network, data center, virtualization — you do what you want."*

![SaiKiran with .zip Application through AMC into IaaS/AWS on Physical Host Machine](images/1_19_amc_iaas_physical_host_diagram.svg)

- To create virtual machines on AWS: use **EC2** (Elastic Compute Cloud)
- We call a server in AWS an **EC2 instance** (a virtual machine)
- In AWS under IaaS: **Network and Virtualization are managed by AWS (Provider)**; **OS, Data, and Application are managed by the Customer**

![AMC / EC2 Diagram with Customer Responsibility vs Provider Responsibility](images/1_20_amc_ec2_customer_provider_diagram.svg)

**IaaS by Cloud Platform:**

| Cloud Platform | Services |
|---|---|
| AWS | Amazon EC2 and Amazon S3 |
| Microsoft Azure | Azure Virtual Machine, VM Scale Sets, Azure Virtual Networks |
| Google Cloud Platform | Google Compute Engine and Google Cloud Storage |

### Shared Responsibility Model (IaaS)

If a hacker attacks your data — whose responsibility is it? **The customer's.** AWS does not have access inside the VM.

> Analogy: You took a flat from a builder. You left it open and a thief entered. It is not the builder's (AWS's) fault — it is your responsibility.

AWS has formalized this as the **Shared Responsibility Model**:
- OS, Data, Application → **Customer's responsibility**
- Network, Virtualization, Data Centers → **AWS's responsibility**

### IaaS Advantages

- **Virtual machines replace physical hardware** — frees up time and creates/destroys on demand
- **Quickly scale up or down** — add or remove machines based on workload
- **Pay only for what you use** — no need to over-provision upfront
- **Suitable for high-performance computing** — vast configurations available in minutes
- **Suitable for predictable workloads** — complete control, cost-effective

### IaaS Drawbacks

- **Operations management** — you are responsible for upgrading, patching, and securing VMs
- **Expensive** — infrastructure is always running; pay for uptime even when idle; capacity planning is critical

## 7. PaaS — Platform as a Service

PaaS says: *"Just give me your application — I'll do everything else. You only manage data and application."*

- No need to create or manage servers
- OS is handled by PaaS
- If a new version of the OS doesn't support your previous version, you are stuck — that's a PaaS drawback

SaaS says: *"I'll do everything — and I don't host your software, I have my own."*

SaaS is essentially **all online software applications** (Gmail, Zoom, Office365, etc.). The customer only uses the software — no control over infrastructure, OS, or even the application itself.

## 9. The 3 T's — Cloud Basic Concepts

Elasticity, Scalability, and High Availability are the three most important concepts in cloud:

---

### 9a. Elasticity

> "Elastic" = stretch when needed, then return to original state.  
> Elasticity in AWS = **increasing or decreasing the number of servers based on load**.

**Elasticity is short-term.**

Example: Flipkart's Big Billion Days — on normal days 2 servers are enough; on sale day we need more → we **stretch** (add servers). After the sale → we **shrink** (remove servers).

![Load Balancer Fanning Out to 4 EC2 App Servers](images/1_30_lb_4_ec2_app_servers.svg)

When load increases, instead of increasing RAM on existing server (which requires stopping it), we **add more servers** — and added 2 more:

![Load Balancer Fanning Out to 6 EC2 App Servers — Elasticity](images/1_31_lb_6_ec2_app_servers_elasticity.svg)

When the sale ends, we remove those 2 servers → **this is Elasticity**.

**Key facts:**
- Elasticity = adding/removing servers based on load
- Achieved in AWS using **Auto Scaling**
- Auto Scaling = **Scale Out** (add servers) + **Scale In** (remove servers)
- Elasticity is also called **Horizontal Scaling**
- Always use the **same capacity** servers in Auto Scaling (equal RAM/CPU) so all users get consistent performance
- Group of EC2 instances managed together = **Auto Scaling Group (ASG)**

---

### 9b. Scalability

> Scalability = **increasing the capacity of the server** itself (RAM, CPU).

**Scalability is long-term.**

Example: Your laptop is slow → you increase the RAM. Same idea for a DB server — if it's slow, increase its RAM/CPU.

To do this, you must **stop the machine** and change the capacity (instance type).

![Scalability: DB Server RAM Increased from 8GB to 32GB](images/1_32_scalability_db_server_ram.svg)

- Use **Elasticity (horizontal scaling)** for application servers at runtime (while customers are using it)
- Use **Scalability (vertical scaling)** for DB servers where stopping briefly is acceptable
- Scalability includes both **Scale Up** and **Scale Down**
- Achieved in AWS by **changing the instance type** (CPU + Memory)
- Scalability is also called **Vertical Scaling**

| | Elasticity | Scalability |
|---|---|---|
| Direction | Horizontal (add/remove servers) | Vertical (upgrade/downgrade one server) |
| Duration | Short-term | Long-term |
| AWS mechanism | Auto Scaling (Scale Out / In) | Change instance type (Scale Up / Down) |
| Downtime needed | No | Yes (brief stop required) |

---

### 9c. High Availability (HA)

> The period of time a service is available to customers = **High Availability (HA)**  
> The period of time a service is NOT available = **Downtime**

**HA is measured in percentages (nines).**

> Never promise 100% availability to a customer — if it ever goes down, you owe them everything back. Promise 99.9999% (like Dettol: "kills 99.99% of germs").

**Three rules for High Availability (RMF):**
1. **Redundancy** = Duplicate — same application running on different machines
2. **Monitoring** = Load Balancer health-checks the application (not just the server) — checks every 30 sec for HTTP 200
3. **Failover** = If one server goes down, another takes over its requests

![Load Balancer Sending to 3 App Servers — HA Example](images/1_34_lb_3_app_servers_ajay.svg)

> **Note:** Load Balancer does health checks on the **application**, not the server. If the app is down but the server is up, LB still considers it dead (no 200 response).

If **all** servers go down → implement Auto Scaling to replace them automatically = **Fault Tolerance** (zero downtime).

**HA Availability Table:**
